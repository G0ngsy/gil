# 실제 방위 센서 연결과 신뢰도 처리 (2026-11-09 시작 · 2026-11-10 검증)

## 문제
앱에는 모의 방향 카드만 있어 실제 센서의 권한·수신·중단을 처리하지 못했다. 경로는 진북 기준인데 브라우저의 나침반 값을 그대로 연결하면 기준/자세/오차 차이로 잘못된 화살표를 표시할 수 있었다.

## 원인
Apple의 `webkitCompassHeading`은 자북 기준이며 `webkitCompassAccuracy`가 -1이면 보정되지 않은 값이다. 표준 절대/상대 방향 이벤트는 같은 오차 필드를 제공하지 않는다. 모의 화면은 시각을 갱신한 고정 입력을 사용하므로 실제 센서 연결에서 그대로 사용하면 오래된 데이터를 유효하게 꾸미게 된다.

## 해결방법
- 실제 GPS 테스트 중 별도의 ‘실제 방향 센서 시작’ 버튼을 제공했다. GPS 위치를 받은 뒤 사용자가 눌렀을 때만 권한을 요청한다. `requestPermission`이 있으면 절대 방향 권한을 요청하며 거부·예외·취소 후 늦은 허용을 구분한다. 버튼 클릭 없이 센서 리스너를 추가하지 않는다.
- `useHeadingTracking`은 권한 후 방향 이벤트를 구독한다. 종료·취소·GPS 중지·도착·경로 변경·탭 숨김·pagehide·화면 해제에서 리스너/타이머를 제거하고 자동 재시작하지 않는다. 화면 해제의 정리는 layout cleanup으로 수행해 passive effect까지 지연하지 않는다.
- `shared/compass.ts`는 나침반 값·보고 오차·GPS 위치/시각·화면 자세를 검사한다. `geomagnetism@0.2.0`의 로컬 WMM으로 자북을 진북으로 보정한다. 외부 서비스에 좌표를 전송하지 않는다. 패키지는 추가 런타임 의존성이 없고 공식 배포본 크기 약 73KB이며 Apache-2.0 라이선스를 `public/licenses/`에 함께 보관한다.
- 모델은 날짜/위치를 키로 한 번 계산해 재사용하며 위치는 약 0.001도 단위 캐시 키를 사용한다. 모델 유효기간 밖, 위도 절댓값 80도 이상, 수평 자기장 6000nT 미만은 보정을 확정하지 않는다. 해수면 높이를 사용하며 오차에는 2도 테스트 여유를 더한다. 이 여유가 실제 정확도를 보장하지는 않는다.
- 첫 구현은 **세로 화면·화면 위쪽·바닥과 나란한 자세(기울기 각 30도 이내)**에서 휴대폰 윗부분의 방향만 지원한다. 세운 자세/가로 화면/뒤집힌 자세/자세 누락은 화살표를 숨긴다. 화면 회전 이벤트에서도 즉시 숨기고 다음 유효 표본을 기다린다.
- 정확도가 포함된 WebKit 나침반 값을 지원한다. 상대 방향 또는 정확도를 알 수 없는 표준 절대 이벤트(일반적인 Android 경로)는 오차를 임의로 만들어 쓰지 않고 지원 제한 문구와 확인 불가 상태를 보여준다. 모든 모바일 브라우저의 방향 안내를 완료한 것은 아니다.
- 1초 넘게 지연된 센서 이벤트는 제외한다. 유효 수신이 처음 5초 동안 없거나 마지막 유효값 후 3초가 지나면 화살표를 지우고 구독을 해제한다. 실제 GPS의 원래 시각과 실제 방위 시각을 유지하고 250ms마다 유효성을 재확인해 GPS가 오래된 경우에도 화살표를 숨긴다.
- 모의/실제 모드는 별도 입력 경로를 사용한다. 실제 GPS에서는 모의 카드/조작을 대신 표시하지 않고 실제 센서 카드만 사용한다. 공통 `DirectionCard`로 800ms 안정화와 확인 불가 즉시 숨김을 재사용한다. 몸 방향이나 AR 공간 추적은 추측하지 않는다.

## 검증 중 발견한 문제

1. 테스트 시계를 실제 현재보다 과거로 멈추려 해 초기 검증이 실패했다. 센서 모델 유효기간 내 날짜를 명시해 설치하고 그 이후 시각으로 정지하도록 고쳤다.
2. 경로 변경 시 리스너 해제 검증에서 잔여 구독이 관측됐다. 정리를 layout cleanup으로 앞당겨도 문제가 남아 추적했고, 새 센서 카드와 지도가 같은 React key를 사용한 것이 원인이었다. key를 역할별로 분리하고 중복 key 경고가 없는지와 구독 해제를 함께 검사하도록 수정했다.
3. 권한 허용 직후 첫 이벤트를 보내는 검사가 간헐적으로 표시 안정화 전에 시간을 진행시켰다. 수신 준비와 유효 표본의 반영을 확인한 뒤 시간을 진행하도록 고쳤다. 799/800ms 경계 자체는 모의 카드 테스트에서 별도로 검증한다.
4. GPS가 만료되면 화살표는 숨겨졌지만 카드가 일반적인 확인 중 문구만 표시했다. 원래 GPS 시각을 검사한 결과가 위치 불가이면 새 GPS 위치가 필요하다고 명시했다.

## 결과

- 단위 테스트: 전체 100개 통과(새 나침반 변환/보정 12개). 공개 모델의 해수면 참조점·보정 부호/랩어라운드·잘못된 오차/자세·GPS 시각·모델 유효기간을 검사했다.
- TypeScript 검사·Vite 프로덕션 빌드 통과.
- 브라우저: 방향 센서 14개 최종 재실행 통과. 기존 모의 카드 7개·GPS 추적 19개도 통과해 관련 40개 범위를 확인했다. 전체 실행에서 나온 첫 표본 준비 실패를 보완한 후 센서 파일 전체를 재검증한 결과이며 실제 장치 대신 방향/GPS 이벤트·권한을 주입했다. 360/430px 가로 넘침 없음과 360px 최종 캡처 육안 확인도 마쳤다.
- 미확인: 실제 휴대폰 센서·OS 권한 창, 자북 보정/자기 간섭의 현장 정확도, 기기별 화면 축·자세 오차, 3초 무수신 기준의 실사용 적합성. API는 방향을 바꿀 때만 이벤트를 보낼 수도 있어 정지 중 재시작이 필요할 수 있다. 최신 원격 배포·TMAP·실제 검색 안내 연결·카메라 AR도 이번 범위 밖이다.

## 사용 방법

HTTPS 또는 localhost의 `/?mode=simulation`에서 현장 경로를 설정하고 ‘실제 GPS 추적 시작’을 선택한다. 새 위치 수신 후 실제 방향 안내의 ‘실제 방향 센서 시작’을 누른다. 세로 화면 상태에서 휴대폰을 바닥과 나란하게 든다. 지원되는 정확도/나침반 값이 없으면 화살표 없이 설명을 표시한다. 이 기능은 테스트 경로를 대상으로 하며 실외 정확도 검증 전 실제 길 안내로 쓰지 않는다.

# 사진으로 주변 장소 확인 — 재검토

최초 검토:2026-11-26. 아래는 구현 전 판단이다. 이후 Tesseract 기반 주변 장소 확인을 구현했다. [확정 계획](plans/photo-place-recognition.md), [구현·검증 결과](issues/2026-11-26-photo-place-recognition.md). VPS/정밀 위치 보정·사진 업로드·실제 현장 사진 정확도 시험은 하지 않았다. AI 지원으로 검토/구현했다.

## 결론
현재 React/Vite/PWA에서는 간판 글자를 읽고 주변 장소 후보를 제시하는 보조 기능을 우선 추천한다. 이름은 ‘사진으로 주변 장소 확인’이 적합하다. 건물/간판 사진 한 장으로 사용자의 정확한 좌표·방향을 알아낸다고 약속하지 않는다.

## 방법 비교

| 방법 | 현재 웹앱 적용 | 준비/제한 | 판단 |
|---|---|---|---|
| 기기 안에서 OCR→TMAP 검색 | 가능성 있음, 시제품 시험 필요 | Tesseract.js 브라우저 실행 지원. 한국어 데이터/worker 로딩과 휴대폰 성능·간판 인식 품질 확인 필요. OCR용 별도 API 키 없이 시작할 수 있으나 TMAP 요청은 기존 키/한도 사용 | 1차 후보 |
| 서버 OCR→TMAP 검색 | 웹 적용 가능 | Cloud Vision 등 텍스트 추출 API와 서버 인증/비용·사진 전송 정책 설정 필요. 현장 사진으로 인식률·지연을 비교해야 함 | 로컬 OCR 시험 결과로 선택 |
| 건물 외관을 기준 영상/지도와 대조하는 VPS | 별도 네이티브 통합 검토 | ARCore Geospatial은 카메라·GPS/센서와 VPS 모델을 결합. 해당 위치의 VPS 지원 여부와 기기/SDK 지원 확인 필요. 현재 웹/PWA의 간판 OCR에 곧바로 붙는 기능이 아님 | 정밀 위치/방향 보정의 후속 연구 |

OCR은 사진의 글자를 읽을 뿐 좌표를 직접 반환하지 않는다. TMAP 검색은 이름/주소/전화번호와 중심 위치 조건 등으로 장소 후보를 반환한다. Google Geospatial은 센서·GPS와 환경 특징 매칭을 결합하는 별도 방식이다. 이들을 같은 정확도의 위치 확인으로 설명하지 않는다.

## 추천 흐름
1. 사용자가 ‘사진으로 주변 장소 확인’을 선택한다. 자동 촬영/업로드하지 않는다.
2. 후면 카메라 촬영 또는 이미지 선택→간판 부분 자르기/재촬영. 원본 전체를 계속 저장하지 않는다.
3. OCR로 읽은 상호·지점명·주소를 보여주고 사용자가 수정할 수 있게 한다.
4. 유효한 GPS가 있으면 해당 주변의 TMAP 후보를 우선 찾는다. 없으면 지역명을 입력받고 범위를 명시한다. 현재 서버는 반경10km 검색이므로 가까운 후보 우선순위/범위는 별도 설계가 필요하다.
5. 후보 이름·지점·주소를 나열하고 사용자가 맞는 장소를 선택한다. 전국의 같은 체인 상호를 하나로 확정하지 않는다. 결과 없음/복수 후보는 수동 검색으로 이어진다.
6. 선택 결과는 **사진에서 확인한 주변 장소**로 표시한다. 장소 중심점/입구 좌표를 새 GPS Fix로 만들거나 가짜 accuracy를 부여하지 않는다. 출발지로 쓰려면 ‘선택한 출발지’로 GPS와 분리하는 후속 구현이 필요하다.

## 왜 사진만으로 GPS/방향 보정이라고 하면 안 되는가
촬영자는 간판 건물과 떨어져 있을 수 있고 길 건너편/다른 층에서 찍을 수도 있다. 같은 브랜드가 여러 지점에 존재한다. 건물 좌표를 알아도 촬영자 좌표·바라보는 방향·카메라 자세를 함께 얻는 것은 아니다. 따라서 이 OCR 결과로 AR 방향 화살표를 켜거나 기존 경로 진행/도착 판정을 갱신하지 않는다. 사진에 위치 메타데이터가 있다는 전제도 두지 않는다.

## 개발 전 확인할 항목
- 주간/야간/반사/흐림/비스듬한 촬영, 한글·영문·지점명·복수 간판·동일 체인·폐업/이전 장소의 실제 사진으로 인식 글자/올바른 후보/실패를 별도로 평가한다. 측정 전 성공률이나 소요 초를 만들지 않는다.
- 로컬 OCR은 사진을 외부 OCR 서비스로 보내지 않는 구성이 가능하지만 worker/언어 모델 다운로드가 발생한다. 한국어 모델 크기/라이선스/로딩/메모리와 낮은 성능의 폰을 확인한다.
- 서버 OCR을 택하면 전송 목적·공급자·보관 범위를 화면에서 설명하고 사진/키를 로그에 남기지 않으며 서버 키·요청 제한·취소/파일 제한을 설계한다. 공급자 데이터 정책/요금은 서비스 선택 시 재확인한다.
- 취소·탭 숨김 시 카메라/worker 해제, 촬영한 사진 삭제, OCR 실패 시 직접 입력 경로를 둔다. 얼굴/차량번호 등 불필요한 부분은 사용자가 간판만 자를 수 있게 한다.

## 검토 당시의 재사용 후보
`src/navigation/LiveCameraGuide.tsx`의 권한/카메라 수명 관리 패턴, `server/navigation.ts`의 검색·중심 좌표와 TMAP 연결, 현재 검색 결과·후보 선택 UI를 활용할 수 있다. 검토 당시 OCR은 미구현이었다. 현재는 Tesseract 기반 사진 주변 장소 확인을 구현하고 운영 엔진/검색까지 확인했다. 사진 업로드 엔드포인트와 사진 기반 정밀 위치 보정은 추가하지 않았다.

## 공식 근거
- [Tesseract.js](https://github.com/naptha/tesseract.js): 브라우저/Node OCR 엔진. 한국 간판 실측 성능 근거는 아님.
- [Cloud Vision OCR](https://docs.cloud.google.com/vision/docs/ocr): 이미지 텍스트 추출 API.
- [TMAP POI 통합 검색](https://tmap-skopenapi.readme.io/reference/%EC%9E%A5%EC%86%8C%ED%86%B5%ED%95%A9%EA%B2%80%EC%83%89): 상호·주소·전화번호, 중심/지역 제한 및 장소 좌표.
- [ARCore Geospatial](https://developers.google.com/ar/develop/geospatial/), [VPS 지원 확인](https://developers.google.com/ar/develop/java/geospatial/check-vps-availability): 센서/GPS/시각적 특징 결합과 지역별 지원 확인.

# 프로젝트 개요

기준일: 2026-11-09 · 코드 기준: `73404ca`

## 문제와 목표

길빛은 목적지 검색에서 도보 경로 확인·이동 안내까지 이어지는 웹 앱을 목표로 한다. 현재는 완성된 내비게이션이 아니라 UI와 센서·경로 처리 흐름을 단계적으로 구현한 프로토타입이다. 사용자는 어디로 가는지, 다음에 무엇을 확인하는지, 위치나 연결을 사용할 수 없을 때 어떤 상태인지를 구분할 수 있어야 한다.

‘고정 예시 거리와 방향이 실제 안내처럼 보일 수 있음’, ‘화면을 닫아도 센서가 켜져 있을 수 있음’, ‘GPS 오차로 단계나 도착이 잘못 바뀔 수 있음’을 구현 과정의 문제로 다뤘다. 이는 코드/이슈에서 확인한 문제이며 사용자 인터뷰로 검증한 요구나 시장 수요는 아니다. 대상 사용자 세분화·인터뷰·사용성 평가 결과는 아직 수집되지 않았다.

## 세 가지 실행 맥락

| 진입 | 목적 | 데이터와 제한 |
| --- | --- | --- |
| `/` | 디자인 시안 | 고정 예시 목적지·거리·화면 전환. 실제 카메라는 별도 선택형 미리보기 |
| `/?mode=live` | 실제 검색용 흐름 | 서버 API와 지도 SDK 연결 코드. 키 미설정 안내 제공, 실제 제공사 인증은 보류 |
| `/?mode=simulation` | 이동 검증 | 모의 좌표 또는 선택형 실제 GPS와 예시/직접 입력 경로. 실제 길찾기 아님 |

`?preview=1`은 디자인 검토용 외곽 도구를 표시한다. 기본 화면은 모바일 전체 높이, PC 최대 480px 앱 영역을 사용한다.

## 설계 선택

- **데이터 정직성:** 모드와 좌표원을 분리하고 실데이터가 없으면 예시로 대신하지 않는다. 현장 경로의 직선 길이를 실제 보행 거리·ETA로 표현하지 않는다.
- **센서 수명 관리:** 사용자 동작으로만 권한을 요청한다. 종료·탭 숨김·화면 이탈·늦은 응답을 처리하고 자동 재시작을 피한다.
- **검증 가능한 계산:** 경로 진행은 UI 밖의 순수 함수로 분리해 같은 좌표열로 재현한다. 실제 기기 검증과 좌표 주입 테스트를 구분한다.
- **디자인 일관성:** 한지색·진녹색·청록색과 명조/고딕 역할을 사용한다. 장식은 [디자인 기준](../../DESIGN.md)에 따르며 지도·카메라 조작에 덧붙이지 않는다.
- **저장 범위 최소화:** 최근 검색/목적지 이름·주소는 기기에 저장하지만 현재 GPS·영상·경로는 저장하지 않는다. 검색 기록에도 장소명이 들어가므로 ‘개인정보를 전혀 저장하지 않는다’고 표현하지 않는다.

실제 검색은 브라우저 → 같은 주소의 `/api/navigation` → 제공사 API로 이어지도록 구현했다. GPS 테스트는 브라우저 위치/모의 좌표 → 공유 진행 계산 → 경로 도식으로 이어지며 제공사 호출을 하지 않는다. 실제 검색 모드와 GPS 테스트를 하나의 실제 경로 안내로 합치는 작업은 남아 있다.

## 남은 단계와 포트폴리오용 수집

1. 최신 코드의 HTTPS 배포 상태를 확인하고 휴대폰 테스트 접근 방법을 준비한다. 과거 배포 주소 존재와 최신 코드 배포는 별개다.
2. 현장 경로로 실외 GPS·권한·중단·이탈·도착을 확인하고 기기/브라우저/시간/오차/재현 조건을 기록한다. 좌표를 공개 자료로 옮기기 전 노출 범위를 검토한다.
3. TMAP 키 연동 재개 시 실제 인증·지도·보행 경로 품질을 확인하고 실제 검색 모드에 추적·재탐색을 연결한다.
4. AR 공간/방향 추적은 별도 미구현 범위다. 필요 범위와 검증 계획부터 정한다.
5. 실제 사용자 과제 수행을 관찰한 뒤에만 사용성 결과를 서술한다. 공개 스크린샷·동영상·기여 범위·회고를 확정해 최종 사례로 편집한다.

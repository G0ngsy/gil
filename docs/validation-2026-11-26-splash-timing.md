# 2026-11-26 스플래시 시간 실측

## 확인 목적
사용자가 현재 연출이 안내한 문 열림→로고→홈 총3초와 다르게 느껴진다고 보고했다. 제품 코드는 바꾸지 않고 운영 주소와 현재 소스를 대조했다.

## 조건과 방법
공개 gilbit.vercel.app, Chrome headless, 390×844, 동작 줄이기 해제, 주소별 새 브라우저 컨텍스트/빈 저장소. requestAnimationFrame으로 최초 연출 DOM이 관측된 시점과 클래스 전환·연출 제거/홈 입력 가능 시점을 기록했다. 내비게이션 시작 기준과 연출 시작 기준을 분리했다. 순서는 refined→기존문→기본이며 같은 브라우저를 사용했다. 네트워크 지연을 고정하지 않은 각1회 측정이므로 보편적인 로딩 성능이나 실기기 보장은 아니다.

| 주소 | 실행 연출 | 내비게이션→연출 시작 | 연출 시작→홈 | 내비게이션→홈 |
|---|---|---:|---:|---:|
| /?intro=refined | 문 개선안 | 1,391ms | 3,009ms | 약4,400ms |
| /?intro=1 | 기존 문 | 130ms | 6,037ms | 약6,167ms |
| / | 기본 매듭 | 124ms | 2,814ms | 약2,938ms |

개선안 상태: closed 0ms → opening 306ms → logo 1,407ms → reveal 2,308ms → 홈3,009ms.
기존 문 상태: closed 0ms → opening 2,033ms → logo 3,618ms → logo-out 4,719ms → reveal 5,220ms → 홈6,037ms.

## 문제
‘총3초’라는 이전 설명은 개선안 자체의 연출 시간만 의미했지만 페이지 로딩까지 포함하는 것으로 해석될 수 있었다. 주소에 따라 다른 연출이 남아 있다는 차이도 설명이 불충분했다.

## 원인
App.tsx는 기본 /에서 매듭, intro=1에서 기존 문, intro=refined에서 개선안을 선택한다. 개선안 타이머는 컴포넌트 시작 후3초이며 초기 HTML/스크립트 로딩 시간은 별도다. 기존 문은 이미지 decode 대기(최대1.5초)에 4.55초 타이머를 추가하므로 이번 측정에서 약6초가 걸렸다. 서비스워커 소스는 앱 번들을 캐시하지 않고 navigate 요청도 네트워크 우선이므로, 이번 측정에서 오래된 번들 캐시 문제의 근거는 없었다.

## 해결방법
이 확인 작업에서는 시간 기준과 주소별 차이를 바로잡아 안내했다. 기본 화면 채택이나 비교용 기존 문을 임의 변경하지 않았다. 향후 ‘3초’는 연출 시작 기준으로 표기하고 로딩을 포함한 총 대기 시간과 구분한다.

## 결과
개선안 자체는 약3초임을 실측했고 기존 문은 약6초, 기본은 매듭 약2.8초임을 확인했다. 사용자가 느낀 차이를 코드만 보고 부정하지 않고 초기 로딩 시간을 따로 기록했다. 제품 코드/첫 방문 저장 정책 변경 없음. AI 지원으로 운영 프레임 측정과 소스 대조를 수행했다. 실기기/모바일 통신 환경·여러 회차 성능은 미측정이다.

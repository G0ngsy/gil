# 원래 목표와 현재 구현 비교 · 방향 기준 안내 복귀 계획

정리: 2026-11-19 · 대조 코드: c1524ab · 상태: **계획, 제품 기능 추가 아님**

## 1. 목표 확정

사용자가 휴대폰을 앞에 들고 멈춰 있어도, 휴대폰이 향한 쪽과 경로를 따라 가야 하는 쪽을 비교해 왼쪽/오른쪽/뒤돌기/정방향을 알려준다. 카메라 화면 위 고정 아이콘이면 충분하다. 바닥·도로에 고정하는 AR, 영상으로 사람 눈·몸의 시선을 인식하는 기능은 요구하지 않는다. ‘바라보는 방향’의 구현 기준은 휴대폰 후면 카메라가 향하는 수평 방향이며 사람이 다른 곳을 보면 실제 시선과 다를 수 있다.

## 2. 현재 구현과 목표 비교

| 항목 | 현재 실제 앱(c1524ab) | 원래 목표에 필요한 상태 |
|---|---|---|
| 위치/경로 | TMAP 검색/보행 경로, GPS 진행·거리·이탈·도착 | 재사용. 위치가 틀리면 방향 목표도 틀리므로 별도 품질 확인 |
| 화살표 의미 | 경로상 다음 행동(예: 30m 앞 우회전) | 지금 휴대폰 방향에서 어느 쪽으로 돌려야 하는지 |
| 정지 후 회전 | 휴대폰만 돌려도 안내 방향은 바뀌지 않음 | 같은 GPS에서 휴대폰을 돌리면 화살표/문구 갱신 |
| 반대쪽 바라봄 | 감지하지 않음 | 후면 카메라 방향이 경로와 반대면 뒤돌기 안내 |
| 카메라 | 영상 위 지도와 같은 JourneyInstruction 카드 | 영상 위 방향 맞추기 표시 + 기존 다음 행동 카드 역할 구분 |
| 실제 방위 센서 | 실제 카메라에서 미사용 | 대상 갤럭시/브라우저/PWA에 맞는 방위 입력과 자세 보정 필요 |
| 남아 있는 실험 | compareFacing/routeBearingAt 및 방위 훅/변환이 검토 화면에 있음 | 계산/오류 처리 재사용 후보. 그대로 연결해 완료할 수 없음 |
| 실험의 제한 | WebKit 방위/각도 오차가 필요하고 세로·수평 가까운 자세만 지원 | Android 입력/품질 판단과 세워 든 후면 카메라 축을 지원해야 함 |
| 지도 위치 표현 | 위치/오차 원/경로 도착점과 장소 위치 분리 | 방위가 유효할 때만 방향 화살촉 추가. GPS 이동 방향과 구분 |
| 재탐색/복원 | 수동 재탐색·기기 내 안내 복원 구현, 권한 자동 시작 안 함 | 유지. 방향 복원은 저장된 옛 값이 아닌 새 센서로 시작 |
| 설치 | PWA 설치 설정/Chrome 설치 조건 확인 | 설치가 센서 지원을 추가하지는 않음. 실제 설치 앱에서 별도 확인 |

현재는 길찾기 데이터와 카메라가 연결된 상태지만 방향 기준 안내는 실제 앱에 미연결이다. 이전 센서 실험의 모의 테스트와 실제 갤럭시 지원 완료를 혼동하면 안 된다.

## 3. 데이터 흐름

1. GPS와 실제 경로에서 사용자의 진행 위치 및 다음으로 따라갈 경로 구간을 선택한다.
2. 그 구간의 지리적 방향을 계산한다. 최종 목적지 좌표를 향한 직선 방향으로 대체하면 건물/도로를 가로지를 수 있으므로 사용하지 않는다.
3. 휴대폰 방위·기울기·화면 회전을 받아 후면 카메라가 향한 수평 방향을 계산한다. 휴대폰 상단 방향과 후면 카메라 방향은 자세에 따라 다르다.
4. 두 방향을 같은 북쪽 기준/시각으로 맞춘 뒤 각도 차이를 계산한다. 자북/진북/임의 상대방향을 섞지 않는다.
5. 유효한 각도 차이만 화살표로 표시한다. 시간·자세·GPS·센서 품질이 불충분하면 방향 확인 중으로 표시하고 확인된 경로 문구를 별도로 제공한다.

예시: 따라갈 길이 북쪽일 때 북쪽을 향하면 정방향, 동쪽을 향하면 왼쪽으로 돌리기, 서쪽을 향하면 오른쪽으로 돌리기, 남쪽을 향하면 뒤돌기다. 이 예시는 개념 설명이며 실제 측정 성과가 아니다.

## 4. 화면 역할을 분리한다

- 큰 표시: ‘조금 왼쪽으로 돌려 주세요’ / ‘이 방향으로 이동하세요’ / ‘뒤돌아 방향을 확인해 주세요’. 이는 현재 경로 방향과 휴대폰 방향 차이다.
- 보조 경로 정보: ‘30m 앞 우회전’ / 남은 거리. 이는 경로의 다음 행동이다.
- 같은 화면에서 두 정보를 모두 ‘우회전’으로 표시하지 않는다. 현재 도로를 따라 정면으로 가면서 30m 후 우회전해야 하는 상황을 구별한다.
- 카메라 배경은 유지하되 바닥에 아이콘을 고정하거나 카메라 영상 분석을 추가하지 않는다.
- 센서 미지원/정확도 불명/오래됨에는 방향 화살표를 숨긴다. 그때 보여주는 기존 경로 문구가 ‘바라보는 방향을 확인했다’고 암시하면 안 된다.

## 5. 구현 순서와 통과 조건

### A. 대상 기기에서 센서 가능성부터 확인

갤럭시 울트라의 정확한 모델/OS, Chrome·삼성 인터넷·설치 PWA에서 권한과 실제 수신 필드/기준/수신 시각/자세를 확인한다. 위치·영상·키는 진단 수집 범위에서 제외한다. 표준 absolute 입력이 온다는 사실만으로 진북/정확도/카메라 축이 맞다고 단정하지 않는다. 각도 오차가 없는 입력에 임의의 ±5° 같은 값을 넣지 않는다.

통과 조건: 정지 상태에서 실제 90°/180° 회전 시 안정적인 절대 방향 및 기준을 확인할 수 있어야 한다. 현재 요구 자세에서 신뢰도를 판단할 방법이 없다면 웹 연결을 완료로 표시하지 않는다.

### B. 방위 입력·자세 보정 계층

Android 표준 방향 데이터와 WebKit 입력을 분리 처리해 공통 데이터 계약(방향/시각/기준/품질 또는 불명)을 정의한다. 세로/가로 화면 회전과 후면 카메라 축을 보정한다. 후면 카메라 축의 수평 투영이 거의 없는 자세 등 방향이 정의되지 않는 경우를 처리한다. 자북→진북 보정은 유효 위치/날짜가 있을 때만 수행한다. 기존 WMM/비교 함수는 재사용 후보이나 품질 모델과 자세 변환은 재설계가 필요하다.

### C. 경로와 방향 비교

기존 GPS 진행·경로 선분을 활용한다. 코너에서는 벽을 가로지르는 직선 대신 유효한 다음 보행 구간을 사용한다. 작은 떨림으로 좌/우가 반복되지 않도록 안정화·경계 구간 처리를 적용하되 수치/지연은 실기기 결과로 조정한다. 이전 800ms나 각도 경계를 검증된 최적값으로 취급하지 않는다.

### D. 지도/카메라 연결

두 화면에 동일한 방향 상태를 공급한다. 지도에서의 방위 화살촉과 카메라 방향 맞추기, 기존 다음 행동 카드를 구분한다. GPS 이동 방향은 보행 진행 확인용 보조 정보일 뿐 정지 시선/기기 방위를 대신하지 않는다. 종료·탭 숨김·페이지 이탈·권한 취소 때 센서/영상 해제를 유지한다.

### E. 모의 + 실제 기기 검증

- 같은 GPS 좌표에서 폰만 0/90/180/270° 돌리면 안내가 바뀌고 남은 거리는 변하지 않는다.
- 코너 전/후의 목표 경로 방향, 반복 회전·경계/떨림, 센서 시각 만료/권한 거부/미지원, GPS 오차/이탈/도착을 검사한다.
- 세워 들기·기울이기·화면 회전에서 부호/축이 뒤집히지 않는지 확인한다.
- 실제 갤럭시에서 정지 회전부터 검증하고 짧은 실외 보행, 카메라/지도 전환, 설치 앱 재실행 순으로 확인한다. 에뮬레이터/주입 값만으로 자기장 간섭·실외 정확도·사용성을 검증했다고 하지 않는다.

## 6. PWA 유지와 Android 앱 선택 기준

우선 현재 PWA에서 대상 기기의 센서 수신·기준을 짧게 확인한다. 현재 서비스 전체를 먼저 갈아엎을 필요는 없다. 다만 웹에서 필요한 방위/품질을 얻지 못하면 이 기능의 신뢰성을 위해 Android 센서 접근 계층이 필요하다. 기존 웹 UI/경로를 유지하는 앱에 실제 네이티브 센서 연결을 추가하거나 Android 앱으로 구현하는 방안을 비교한다. 웹을 APK로 포장하는 것만으로 센서 문제를 해결했다고 해서는 안 된다. 어떤 방식을 선택하든 기기 센서 자체의 오차·간섭은 남아 실제 검증이 필요하다.

현재 결정은 ‘웹에서 반드시 가능’ 또는 ‘지금 바로 네이티브 전환’이 아니다. **첫 실행 작업은 갤럭시 실기기 센서 확인과 카메라 방향 축 정의**이며, 그 결과로 구현 경로를 정한다.
